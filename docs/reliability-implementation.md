# Implementation of the 16 reliability risks

Implemented locally on 10 October 2026. This supersedes the proposed fixes in the original [review](multi-user-review.md). Hosting, production database migration, backup restore drills, provider failover, and production capacity validation remain deployment activities.

| R1: invitation identity                | Invitation discovery no longer trusts an account's typed email. The recipient must possess the shared token and request access. Only the Celestial can confirm the specific applicant and grant membership. The UI asks the Celestial to verify the person through a trusted contact. No SMTP integration.                                                                                                   | Confirm intended identities before approval; review existing memberships, which are preserved rather than retroactively verified. | R2: partial writes                     | Replica-set transactions cover team/owner creation, invitation approval/membership, mission/comment changes and activity. Reads fetch users and mission deletion state only for the returned page.                                                                                                                                                    | Run migration to backfill retained old history. ## Deployment and migration

The user's `server/.env` and configured MongoDB data were not changed or used by the automated tests. MongoDB Atlas normally supplies replica-set infrastructure; verify the target configuration. Standalone MongoDB is no longer supported for crew writes.

For the project's managed local database, stop and restart the managed process to enable `planner-rs`; existing data is preserved. Do not stop a MongoDB installation owned by another project. The local script checks the managed database path and refuses to manage a different installation.

Before upgrading an existing database, take a backup, pause writes, run one migration operator at a time, inspect the invariant report and resume only after validation. Set `DB_ADMIN_CONFIRM` to the **exact target database name** before migration or retention writes; URI and credentials stay in private environment configuration.

```powershell
npm.cmd run build
# Use the intended environment's private DB configuration.
$env:DB_ADMIN_CONFIRM = 'your-target-database-name'
npm.cmd run db:migrate -w server
npm.cmd run db:audit -w server
npm.cmd run db:retention -w server
# Only after reviewing the preview and backup:
npm.cmd run db:retention -w server -- --apply
```

Production settings: `NODE_ENV=production`, exact HTTPS `CLIENT_URL`, `VITE_API_BASE_URL=/api/v1` at build time, private `SESSION_SECRET`, replica-set `MONGODB_URI`, and `DB_POOL_SIZE` (default 20 per process). Keep `TRUST_PROXY_HOPS=0` until the proxy is verified. If enabling it, also set `PROXY_TRUST_CONFIRMED=true`. Start with `npm run start -w server`; the compiled frontend must exist.

The migration copies only still-retained embedded history from the last 365 days, using event IDs to avoid duplicates. It does not silently change existing roles or drop old indexes. Existing legacy missions without approval state become approved, preserving their prior behavior. Run it before opening the upgraded UI to existing users so historical activity and member search are populated.

## Validation

Automated checks run against disposable replica sets and synthetic browser fixtures. All 125 tests passed (58 frontend, 67 API), as did 100 responsive browser checks. TypeScript, lint, formatting and production builds passed. The final password-worker lifecycle guard was also verified with 24 authentication/reliability tests. Browser checks cover Chromium viewport behavior, not real-device Safari.

`npm run test:load` builds and launches a disposable production-mode API with a temporary database, then tears both down. It cannot select the configured application database. The production startup, migration and SPA/API/asset routing paths are included.

The larger local smoke run used 50 concurrent synthetic sessions, 10,000 seeded missions and 1,000 comments. All 1,000 mixed read requests returned 200 on both runs. The final repeat measured 217 requests/second, p95 315 ms and p99 390 ms (the first measured 155 requests/second, p95 443 ms and p99 483 ms). This short local test validates the shared-store/production startup path under modest concurrency, not production user capacity, internet latency or sustained load. It also exercises 100 API mission creations before the read workload; larger datasets are inserted directly into the disposable database. The report is written to ignored `.local/load/report.json`.

The wider staging load ramp, real-provider fault/restore drills, proxy validation, and final-domain mobile/Safari checks in the [deployment plan](deployment-plan.md) remain release gates.
