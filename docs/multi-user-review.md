# Multi-user reliability review

Reviewed: 10 October 2026. Scope: current React/Express/Mongoose implementation, authentication, crew roles, invitation links, missions/proposals, comments, deployment configuration, and data-access paths.

**Assessment:** suitable for continued development and staging evaluation. Public multi-user readiness and a supported user count are not established. The main release blockers are invitation identity and multi-document consistency. Several scaling problems depend on crew size rather than total registered users.

This is a static code review. Scenarios below are inferred from the implementation unless described as existing behavior; crash injection, load tests, and production proxy verification were not performed for this review. Existing unit/integration and fixture-based responsive checks provide useful correctness coverage, not capacity evidence.

Priority: **P0** before public access; **P1** before a wider pilot or multiple replicas; **P2** as usage/data grows. Recommendations are future work, not completed fixes.

## Release blockers

### R1 — P0: email matching does not prove invitation identity

Evidence: [registration](../server/src/modules/auth/auth.service.ts), [invitation discovery and acceptance](../server/src/modules/invitations/invitation.service.ts), [auth routes](../server/src/modules/auth/auth.routes.ts).

Registration accepts an email without verification. Incoming invitations are found using that address, and invitation responses compare it to the account email. Someone who registers an intended recipient's unused address can discover and accept the invitation; strong random tokens and hashing do not fix an unverified account identity. Existing accounts cannot be impersonated simply by registering the same email because uniqueness is enforced.

Fix: verified identity before invitation discovery/acceptance, or a deliberate manager approval workflow with no automatic membership grant for unverified accounts. SMTP is not required for sharing links; a verified identity provider is one option. Do not leak pending invitation details to unverified accounts. Verify that a falsely claimed address cannot list, open, or accept another person's invitation, including without knowing its token.

### R2 — P0: process failure can split related writes

Evidence: [team creation and removal](../server/src/modules/teams/team.service.ts), [invitation response](../server/src/modules/invitations/invitation.service.ts).

Team creation saves the team and then its owner membership. An exception triggers compensation, but termination between writes can leave an orphan team. Invitation acceptance marks the invitation accepted before upserting membership; termination in between leaves an accepted invitation without access, and retry cannot complete it. Member removal deletes membership before clearing assignments, so a crash or partial failure can leave stale assignees.

Fix: transaction-backed team creation and invitation acceptance on a replica set, retry handling, and idempotent responses. For large assignment cleanup, use bounded batches with persisted progress or an outbox/repair process rather than an enormous transaction. Define which invariant must be immediate and which may be repaired. [MongoDB transactions](https://www.mongodb.com/docs/manual/core/transactions/) support atomic multi-document changes on replica sets/sharded clusters; the existing embedded mission/history writes already benefit from single-document atomicity.

Acceptance: kill/restart the process between each related write in isolated staging; retry the original request; prove there is one membership, no inaccessible accepted invite, and no orphan team/stale assignment after the defined repair window.

## Existing protections worth preserving

- Backend membership and role checks enforce Celestial/Holy Knight/Commoner rules, independent of hidden UI controls. IDs are scoped to team/mission; passwords are hashed, sessions are HttpOnly, mutations require a trusted Origin, and invitations use random hashed tokens with 48-hour expiry and atomic one-time claiming.
- Unique email/membership/token/pending-invitation indexes and atomic mission/comment version filters prevent several duplicate and concurrent-write failures. Mission/comment changes and embedded history are saved together. Some cross-document races have post-write reconciliation; those checks reduce risk without providing crash atomicity.
- Lists are bounded per page, history is bounded per record, sensitive request content is omitted from logs, and UI loading/empty/error states and conflict flows exist. These should remain in the new design and deployment work.

## Recommended implementation order

1. Identity-safe invitation discovery/acceptance, atomic team/invitation writes, and a recoverable removal workflow.
2. Shared-network-friendly limits, explicit timeouts/readiness/metrics, mandatory write versions and idempotent creates.
3. Bounded member selection/cleanup, activity redesign, query-plan tuning and cursor paging.
4. Isolated staging load/fault tests and a backup restore drill; select hosting size from measurements.
5. Closed pilot, then a monitored public release. Add multiple API instances only after shared limits and pool/proxy verification.

Follow the [deployment plan](deployment-plan.md) for configuration, test gates, rollout and rollback. No fixed claim such as “supports 1,000 users” is justified by this review: concurrent activity, data size, network latency, hosting resources and request mix determine the practical limit.
